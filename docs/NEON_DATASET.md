# Neon training dataset source

Koschei Sentinel v0.8 can build a training-ready release directly from the production Neon database without writing a raw ARVIS export file.

## Source boundary

The command reads only these fixed public tables:

- `security_unified_radar_verdicts` for signed final verdicts and triggered rules;
- `security_radar_verdicts` for the latest signed result from each ARVIS module;
- `security_radar_holder_snapshots` for bounded top-holder context.

Before reading records, Sentinel checks that every required table and column is present. Schema drift fails closed.

The connection is placed in a read-only PostgreSQL transaction with a bounded statement timeout. The command contains no INSERT, UPDATE, DELETE, DDL, or migration path.

## Secrets

Store both values only in a secret manager or runtime environment:

```bash
NEON_DATABASE_URL=
SENTINEL_DATASET_SALT=
```

The database URL is never included in a manifest, release, test artifact, provider diagnostic, or controlled error message. The salt is used only for deterministic HMAC pseudonymization and is never written to the release.

For Google Colab, save both values in Colab Secrets and enable notebook access. Do not paste either value into a notebook cell or chat message.

## Install

```bash
pip install -e '.[dev,neon]'
```

`psycopg` is an optional dependency. Normal CI, inference, evaluation, and fixture dataset workflows do not install it and do not connect to Neon.

## Validate without materializing

```bash
sentinel-neon-build \
  --salt-version production-2026-08 \
  --policy configs/readiness/training-ready.v1.json \
  --dry-run
```

The default source limit is 5,000 latest signed targets. It can be reduced or raised to at most 10,000 with `--limit`.

A dry run still performs the complete read, conversion, pseudonymization, leakage-safe split, digest verification, and readiness evaluation. It does not preserve the temporary release.

## Materialize a passing release

```bash
sentinel-neon-build \
  --output-dir build/releases/sentinel-v0.8-training \
  --salt-version production-2026-08 \
  --policy configs/readiness/training-ready.v1.json
```

The final directory is created only when all export, privacy, duplicate, split, lineage, diversity, confidence, concentration, and readiness checks pass.

Raw wallet addresses, target IDs, verdict signatures, evidence IDs, and lineage values exist only in memory until the existing Sentinel exporter pseudonymizes them. Only canonical `sentinel.dataset.v1` rows and deterministic manifests reach the release directory.

## Evidence mapping

Each latest signed unified verdict becomes one training example per target.

- Triggered unified rules become rule-linked evidence with their stored evidence status.
- Latest signed module verdicts become module-specific contextual evidence.
- Holder snapshots contribute only aggregate count and concentration values; owner wallets are not copied into evidence attributes.
- A signed scan-summary fallback is used only when no rule, module, or holder evidence exists.

The signed deterministic verdict remains final. The training target continues to be generated by the policy-valid deterministic Sentinel baseline.

## Exit codes

- `0`: the dataset is ready; it is materialized unless `--dry-run` was used.
- `2`: source, schema, privacy, contract, duplicate, or database validation failed.
- `3`: the dataset is structurally valid but below the configured readiness policy.
