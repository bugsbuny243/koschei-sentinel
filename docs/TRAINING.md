# Koschei Sentinel Training

Koschei Sentinel v0.6 adds the first executable adapter-training lane. The lane is deliberately split into a deterministic planning phase and an explicit GPU execution phase.

## What this phase trains

The trainer performs supervised QLoRA/LoRA fine-tuning against a pinned base-model revision. Each training row contains:

1. the fixed Sentinel system contract;
2. one pseudonymized `sentinel.case.v1` evidence packet;
3. one policy-valid `sentinel.opinion.v1` target.

The initial target is generated by the deterministic Sentinel baseline. This teaches the adapter the exact output shape, evidence citation discipline, authority boundary, confidence ceiling, and abstention behavior. It does not yet add new expert knowledge. Later dataset releases can replace baseline targets with reviewed expert commentary while keeping the same validation gates.

## Safety properties

- The base model must use an `owner/model` registry identifier.
- `base_revision` must be a full 40-character immutable commit SHA.
- `trust_remote_code` is permanently false in the v1 contract.
- Dataset and output paths must remain inside the repository root.
- Every train, validation, and test digest is checked against the signed quality manifest before model loading.
- Dataset rows are parsed again as `sentinel.dataset.v1`.
- Supervised answers are validated against the Sentinel evidence policy.
- Existing output directories are never overwritten.
- Adapter artifacts receive a deterministic content digest and `sentinel.adapter-manifest.v1` manifest.
- Normal CI performs no model download, network call, GPU operation, or paid inference.

## Prepare a real dataset release

Export and split ARVIS evidence using the existing privacy and leakage gates. The resulting directory must contain:

```text
quality-manifest.json
train.jsonl
validation.jsonl
test.jsonl
```

The training planner rejects dry-run manifests, malformed rows, count drift, digest drift, missing split files, an empty train split, path escapes, and mutable base-model revisions.

## Validate the training plan

Copy the example config and replace:

- `base_model` with the chosen Hugging Face model identifier;
- `base_revision` with the model repository's full immutable commit SHA;
- `dataset_release` with the real Sentinel release directory;
- `run_id` and `output_dir` with unique values.

Then run:

```bash
pip install -e '.[dev]'
sentinel-train \
  --config configs/training/qlora.colab.example.json \
  --plan-output build/training/colab.plan.json
```

This phase is network-free and does not require the training dependencies. Inspect the plan before allowing GPU execution.

## Execute on Google Colab or another CUDA host

Use a GPU runtime, place the private repository and materialized dataset release in the runtime, then install the optional training stack:

```bash
pip install -e '.[dev,training]'
sentinel-train \
  --config configs/training/qlora.colab.example.json \
  --plan-output build/training/colab.plan.json \
  --execute
```

The trainer loads the pinned base revision with 4-bit or 8-bit quantization, prepares it for k-bit training, injects LoRA adapters, masks system and user prompt tokens from the loss, trains only on assistant output tokens, and writes the adapter atomically.

Expected output shape:

```text
build/training/<run-id>/
  adapter/
  adapter-manifest.json
  checkpoints/
```

Do not commit model weights, private dataset releases, Hugging Face tokens, or runtime secrets to this repository.

## Promotion remains separate

A completed adapter is not automatically trusted or deployed. The next phase must add a local PEFT inference adapter, run the expanded Sentinel benchmark, compare it against the deterministic baseline and Together reference candidates, and refuse promotion when any hard authority, grounding, abstention, privacy, or confidence gate fails.
